# 重要性の判断

## 観点

「確かめた事実」と「Issue で追跡する重要性」を分けて書く。事実が成り立っても、重要とは限らない。重要性は、次の観点で、その問題を読んだ人・使った人が次に何を誤るかまで追って決める。

| 観点 | 確かめること |
| --- | --- |
| 到達可能性 | 通常の入口・入力・環境で起きるか。限定的な入力なら、その入力を書く人がいるか |
| 影響 | 停止、誤った結果（黙って別の対象・設定を使う、成功に見えて空振りする）、データ損失、秘密の流出・権限や検査の迂回、繰り返す運用上の支障 |
| 頻度と回避策 | 実際に起きた回数、別のセッション・別の PR での発生、利用者が気づけるか、回避できるか |
| 表示と実体 | 利用者に見える表示（`--help`・案内・文書）と、実際の処理・呼び出し元の分岐。内部の説明の食い違いが、表示や処理に届くか |
| 後の作業 | 文書・記録の誤りなら、それを読む人の次の操作（当てる差分、番号からの参照）と、それを読む処理の有無 |

## 型ごとの例

例はすべて型として書く。実際の再調査の記録は Issue #45 と、各 PR の事後調査コメントにある。

| 型 | 結論 | 要点 |
| --- | --- | --- |
| 通常の書き方の入力で、黙って別の設定・対象が使われる | 新しい Issue | 対照（意図した側と誤って選ばれる側に別の値を置く）で、実際に使われるものが変わるところまで確かめる。限定的な入力なら、その条件も Issue に書く |
| 重大度の表記は低いが、秘密が公開される・範囲の外を消す経路がある | 新しい Issue | 表記ではなく経路で判断する。秘密が今も公開されていれば、投稿の前に利用者へ知らせる |
| 一度直した問題が既定ブランチで再発している | 新しい Issue | closed の Issue を reopen せず、新しい Issue から closed の Issue と原因の変更へリンクする |
| 記録の外の候補（PR 本文の検証の失敗）が、別の実行でも繰り返す | 新しい Issue（原因が未確定なら調査 Issue） | 頻度と、別の PR・セッションでの発生を根拠にする。推定の原因は推定と書く |
| 元の候補は見送るが、別の形式の入力で別の影響が見つかった | 元の候補は見送り、新しい影響だけを起票 | 元の候補を抱き合わせで起票しない。範囲を分け、前の評価を補足・訂正する |
| 将来の予定の後に条件がそろう | 予定を一次情報で確かめてから判断する | 予定の出典（Issue・PR）を書く。確かめられなければ確認不足 |
| 内部の説明文（docstring など）が実際の出力と食い違う | 見送り（表示・処理に届かない場合） | `--help` の表示、利用者向けの文書、実際の出力、呼び出し元の分岐まで追う |
| 誤った使い方のときの案内の文面が原因と違う | 見送り（止まって処理が進まない場合） | 終了コードと、後続の処理が始まらないこと、案内に入力の値（秘密を含みうる）が出ないことを確かめる。案内に従った次の操作で処理が進んでしまうなら、見送りにしない |
| 文書の記録の誤り（経緯・番号の種別） | 見送り（次の作業・参照を誤らせない場合） | リポジトリの外の事実は、clone や本文の転記をせず、API の patch・commit の比較や、番号の転送の実際の挙動で確かめる。見直す条件を、その文書を次に編集する作業に結び付ける |
| レビューした tree と既定ブランチの tree が同じ | 再実行しない理由を書く | tree の一致を確かめ、挙動の変更が無いので再実行しなかったと書く |
| 集約先の open の Issue に、同じ問題の再現・影響・直す箇所がそろっている | 既存 Issue に集約、コメントしない | 元 PR のコメントに対応だけを書く |

## 確かめ方の区別

| 書き方 | 意味 |
| --- | --- |
| コードを読んだ | 実行していない。挙動の主張は推論 |
| fake のコマンド・一時 HOME で実行した | 実際の CLI・モデル・サービスは使っていない |
| 実際の sandbox・実際の Git で実行した | その環境の範囲で再現した |
| 実際のモデル・サービスで E2E を実行した | 外部の振る舞いまで確かめた |

実行していない確認、失敗・時間切れ・環境の不足は「再現しない」「影響なし」にしない。確認不足として、足りない確認を書く。
