# 投稿する本文の形

`<…>` は値に置き換える。値の無い節は消す（空の見出しを残さない）。どの本文にも、ローカルの絶対パス・環境変数の値・トークン・ログの全文を書かない。判断 ID は `fold` の `id` と同じ完全な形（`<ファイル>#<ID>@<HEAD の先頭 12 桁>`）で書き、記録の外の候補は `記録外-<n>（出典: <PR 本文の節名など>）` と書く。

## 元 PR への事後調査コメント

1 行目のマーカーと 2 行目の見出しは変えない。次の再調査で前回の事後調査として見つけるための目印である（`scripts/previous_followups.jq`）。本文に `<!-- review-fix-planning:` と `<!-- review-records:` で始まる文字列を書かない（引用・コードブロックの中でも）。判断の記録として読まれ、PR 修正の判断が変わる。

```markdown
<!-- review-carry-over-followup:v1 -->
## 持ち越し候補の再調査（<モデル識別子>）

対象 PR: #<番号>（<open・マージ済み・未マージで close 済み>） / 調べた commit: `<完全な SHA>`（<PR の head・既定ブランチの最新>） / 元のレビューの HEAD: `<先頭 12 桁>`

| 候補 | 結論 | Issue |
| --- | --- | --- |
| `<判断 ID>` | <新しい Issue・既存 Issue に集約・見送り・確認不足・採否未決のまま終わった候補> | <#番号 または ―> |

### `<判断 ID>` — <結論>

- 指摘: <一行の要約>
- 確かめた事実: <成立する条件、通常の利用で起きるか、影響、頻度、回避策>（確かめ方: <コードを読んだ・fake のコマンドで実行した・実際の環境で実行した>）
- 結論の理由: <Issue にする理由／集約先と、その Issue に足した事実／Issue にしない理由>
- 残る制約: <見送る場合は、未修正のまま残る点。見送りは解消済みではない>
- 足りない確認: <確認不足の場合だけ。何が足りず、誰がどの環境で確かめられるか>
- 見直す条件: <どうなったら判断を見直すか。Issue にした候補は「Issue で追跡する」>

### 前回の事後調査との関係

- <前回のコメントの URL> の `<判断 ID>` を補足・訂正する: <前回の後に何が変わったか、どの結論をどう変えるか>

### 確かめていないこと

- <実行していない確認と、その理由>
```

- 全件を見送る場合も、一部を起票した場合も、見送る候補ごとに理由と見直す条件を書く。「重要でない」の一言や、重大度の表記・票数・直しやすさだけで済ませない
- 集約は、表の Issue 列に集約先の番号を書く。集約先へのコメントはこのコメントの後に投稿するので、URL ではなく「<Issue> に事実を足した」と書く。新しい事実の無い集約は、節に「<Issue> に再現・影響・直す箇所がそろっており、新しく分かったことは無いので、<Issue> には書き込んでいない」と書く
- 2 回目以降で前提の変わらない候補は、節を書かず、表の結論に「前回のまま（<前回のコメントの URL>）」と書く
- open の PR で判断を見直す根拠を得た候補は、結論を「PR での再判断が必要（review-fix-planning）」とし、得た根拠（実行した再現の入力・結果）を書く

## 新しい Issue の本文

```markdown
## 概要

<何が起きるか。原因が確定していなければ「調査」と書き、確定したバグと断定しない>

## 根拠

- 調べた commit: `<完全な SHA>`（<既定ブランチ・PR の head>）
- 再現の条件: <入口・入力・環境>
- 観測した結果: <実行したコマンドの形と結果。対照を取ったならその結果も>
- 限定される条件: <起きない条件、確かめていない条件>

## 影響

<通常の利用で起きるか、頻度、誤った結果・停止・データ損失・安全性のどれか、回避策>

## 期待する挙動

<…>

## 受け入れ条件

- [ ] <…>

## 出典

- 元 PR: #<番号>、判断 ID: `<判断 ID>`（<元の判断: 見送り・採否未決など>）
- 元 PR の事後調査コメント: この Issue の後に投稿するので、「元 PR のコメントから辿れる」と書く
- 既存 Issue の検索: open・closed の両方で <検索した語> を探し、同じ問題は見つからなかった（<関係する Issue があれば番号と関係>）
```

利用者の名指しで起票した場合は、概要に「<利用者の依頼> により起票した。重要性の評価: <…>」を書く。

## 集約先の既存 Issue へのコメント

その Issue にまだ無い事実があるときだけ、元 PR の事後調査コメントを投稿した後に 1 件書く。利用者の承認・判断を求める書き方、claim やボードのマーカー、担当を名乗る記述は書かない。

```markdown
## PR #<番号> の持ち越し候補の再調査（<モデル識別子>）

元 PR の事後調査: <URL> / 判断 ID: `<判断 ID>` / 調べた commit: `<完全な SHA>`

- 確かめた事実: <この Issue にまだ無い事実>（位置: `<path>:<line>`（`<SHA の先頭 12 桁>` での位置）。確かめ方: <コードを読んだ・fake のコマンドで実行した・実際の環境で実行した>）
- 見直す条件: <…>

この事実をこの Issue の範囲に含めるかは、この Issue の担当が決める。含めない場合は、担当の Spec に一行書く。
```
