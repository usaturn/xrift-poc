### 効いた型と効かない型

- 効いた型: 候補に入っていたのに判定しなかった（E4・C-I1）。候補を全件判定させ、判定漏れを `validate` で検出する形にしたことで、見落としが起きなくなった。
- 効かない型: (1) 候補に入ったのに判定を誤る（#334 の README の行）。(2) 変更対象そのものが文書・テンプレートで、差分から語がほとんど取れない（#416）。

### 残る課題

- 変更対象が `.md`・`.rst` のとき、語がほとんど取れない（#416 は 3 語）。
- 判定そのものの誤りには効かない。判定の根拠（どの行のどの語を照合したか）を残す形にしても、誤った consistent は防げない。
- 空白を含むパスの扱い（段階3 の ledger の deferred minor）。
- 1 回ずつの実行で、統計的な保証ではない。

## 7. K-3: 過去の PR の再生評価（#547 段階3）

### 方法

- 1 回目のサイクルの HEAD で、今のレビュアー 4 人（claude-opus-5-5、SWE-2 Max、deepseek-v4.1-flash、gpt-6.1-sol）が新しい pr-review で探す。review-verify（`mode: cycle`）で確かめる。review-fix-planning の判断の規則で採否まで決める。
- 正解集は、再生の前に確定した。#485 の分析、状況コメントの編集履歴、後の commit から作った（`$EVAL/k3/ground-truth/`）。
- 採点の区分（Spec 5.2）:
  - (a) 必要だった修正: 今の規則で「対応する」（H・D1・N）になり、1 回目の HEAD にすでにあった欠陥。Spec 5.2 は #485 の分析から、#484 の C-H1・C-M1 だけを想定していた。正解集を確定するとき、#334 の A-1 と #484 の A-1（G-M1）を、今の安全性の再評価（#534）に当てはめて加えた。したがって (a) は #334 が 1 件、#416 が 0 件、#484 が 3 件である。
  - (b) 後で見つかった既存の欠陥: 1 回目の HEAD にあったが、2 回目以降のサイクルで見つかったもの（採否は問わない。発見の指標にする）。
  - (c) 修正が持ち込んだ不具合: 当時の修正 commit が持ち込み、後のサイクルで見つかったもの（fix_check の指標。6 章の表）。
  - 誤採用: 再生の決める工程の Fix のうち、(a) に無く、正解集の根拠から見て直す必要の無いもの。
- 「1 回で収まる見込み」（Spec 5.6）: (a) がすべて 1 回目の Fix に入り、誤採用が 0 件の場合とする。実際に修正を書いていないので推定である。(a) が空で誤採用も 0 件なら、条件は形の上だけで満たされる（#416）。(c) の再生結果は、修正が持ち込む不具合を push 前に止められるかの参考で、この見込みには含めない。
- 修正の確認の再生: 各 PR で、正解集が推薦した 1 組の commit に対して、段階3 の fix_check を実行した（6 章）。この組は歴史上のあるサイクルの修正であり、再生の決める工程が出した Fix ではない。再生の流れのままなら、その修正は書かれず、(c) の不具合もそのサイクルでは生じない。したがって (c) の再生は、修正の確認が持ち込まれた不具合を見つけられるかを見るもので、再生した流れの続きではない。
- 出典: `$EVAL/k3/{334,416,484}/result.md`、集計は `$EVAL/k3/stats.json`。PR #542 の行は 3 章の結果と 6 章の K-1 を合わせたもの。
