# PR レビュー時間予算と委譲規約

この文書は PR レビュー実行時の時間予算・規模判定・委譲・打ち切りの規約である。
文面の規約であり、モデルの行動や実時間保証ではない。時間制御の行動保証とは扱わない。

## 時間予算

- 規定値は全体 45 分、調査終了は開始 40 分、確定・保存・後片付けの予約枠は 5 分である。
- 調査の絶対期限は `research_deadline = 開始時刻 + 全体予算 − 予約枠`。非対話では実requestの残り期限を全体予算の上限にも使う。ユーザーまたはcallerが明示した予算は開始時に確定し、途中で延長しない。
- 5 分以下の指定では新規調査を開始せず、限定結果または開始不能理由を返す。
- 開始時刻は最初の PR API 呼び出しより前に UTC と epoch 秒で取得し、シェルの変数が次回呼び出しにも残ると仮定せず、取得した値をセッションの進捗記録に保持する。予算・調査期限・phase・委譲状態は進捗とdraftのReview coverageへ記す。開始UTCと経過のv2実測はprepare/completeが同じ値でReview timingと候補へ記録する。非対話の最終応答はJSONだけにする。

```bash
REVIEW_STARTED_EPOCH=$(date -u +%s)
REVIEW_STARTED_AT=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
REVIEW_TOTAL_SECONDS=2700
REVIEW_FINALIZE_SECONDS=300
REVIEW_DEADLINE_EPOCH=$((REVIEW_STARTED_EPOCH + REVIEW_TOTAL_SECONDS))
RESEARCH_DEADLINE_EPOCH=$((REVIEW_DEADLINE_EPOCH - REVIEW_FINALIZE_SECONDS))
```

- 開始からの目安は次のとおり。準備が遅れても期限は起点から固定し、候補が残らなければ早く保存する。

| 開始からの目安 | 処理 |
| --- | --- |
| 0〜5 分 | PR 情報、ref、worktree、差分、規模、委譲可否 |
| 5〜35 分 | 本体の精読・反証・必要な実行検証。委譲はこの区間と重ねる |
| 35〜40 分 | 候補と既存指摘の判定、未検証箇所の整理 |
| 40〜45 分 | 委譲停止確認、draft、HEAD 確認、save、cleanup、報告 |

- phase 境界、モデル・ツール呼び出しから戻った直後、委譲開始前、新しい候補や実行検証の開始前に現在時刻を確認する。単独の時刻確認だけのために推論往復を増やさず、独立した通常コマンドと合わせられる場合は合わせる。ターンを跨いでも起点と期限を維持する。

## 規模判定

- prepareが固定したbaseからreviewed_headまでの `git diff --numstat` と `--name-only` を使う。指定commitの規模にlive PR APIの現在headの規模を混ぜない。規模だけのAPI往復を増やさない。
- 追加行数+削除行数と変更ファイル数を使う。diffのヘッダーやcontext行と区別する。
- 不明・取得失敗・binaryの数値でない表示は0にせず、小規模とみなさない。PR headとworktree commitの整合はprepare/completeが検査する。
- 変更量 300 行以下、変更ファイル 3 個以下の両方を満たせば既定は本体のみとする。片方を超えても自動委譲しない。
- バイナリ差分、規模不明、セキュリティ・データ破壊・互換性に関わる変更は行数だけで軽量判定しない。それでも委譲は必須ではない。

## 委譲

- 読み取り専用の補助委譲は最大 1 件とする。起動条件は次のすべてを満たすこと。無条件の委譲はしない。
  - 独立して調査できる範囲がある。
  - 本体側にも同時進行する仕事（精読・反証・実行検証）がある。
  - 残り調査枠が 10 分以上ある。残り調査枠が 10 分未満なら新規委譲しない。
  - 起動、期限付き待機、停止、停止確認の機能を実際のランタイムで利用できる。バックグラウンド起動と停止・停止確認ができるランタイムに限り、同期起動のみのランタイムでは委譲しない。ランタイム別の起動可否は `.agents/monitoring-runtimes.md` に従う。停止手段を利用できなければ委譲を省略する。未確認の API 名、PID、ツール権限を推測しない。省略した場合は理由を進捗記録に残す。
- 追加委譲・再委譲・委譲先からの再委譲はしない。
- 委譲範囲は変更箇所の呼び出し元・呼び出し先の調査、依存関係ファイル（pyproject.toml / package.json / lock ファイル等）の確認、変更に対応する既存テストの探索に限定し、変更ファイル本体の精読は委譲範囲に含めない。指摘の根拠となる精読をサブエージェント任せにしない。
- 確度ラベルの最終判定は、メインエージェントが根拠（コードパス・実行結果）を直接確認した上で行う。サブエージェントの報告のみを根拠に【検証済み】を付けない。
- 起動は差分と規模の確認後、本体精読の完了前とする。
- 委譲の絶対期限は `min(起動時刻 + 10分, research_deadline)` とする。進捗があっても延長しない。
- 最後の実質進捗から 5 分で早期打ち切りとする。最初の進捗前は起動時刻を基準とする。これはハング判定ではなく、補助調査に割り当てた予算の終了である。
- 実質進捗とは「対象コードパス、確認した挙動、結論または残る具体的疑問」が増えたことである。heartbeat、同じ状態の反復、単なるログ更新では無進捗時計をリセットしない。委譲先には途中結果を出せる区切りで共有させる。
- 委譲 prompt の必須欄は次のとおり。実際の起動時は具体値を埋める。

| 欄 | 渡す値 |
| --- | --- |
| 対象 | 固定 HEAD と WT の完全パス、委譲範囲の限定内にある独立した調査範囲 |
| 期限 | 起動時刻、絶対期限、実質無進捗 5 分 |
| 制約 | 読み取り専用、再委譲禁止、reviews と既存レビュー本文へのアクセス禁止 |
| 中間出力 | ファイル・行、確認した挙動、根拠、残る具体的疑問 |
| 終了 | 期限で親が停止する。返せる根拠は途中でも報告。保存は親が行う |

- `reviews/`、既存レビュー本文、`PREVIOUS_REVIEW`、判断の記録（手順 3 の集約の結果）は渡さない。保存と履歴の解釈は親だけが行う。
- 本体の仕事が残る間は委譲待ちをしない。待機が必要ならランタイムの通知・待機を使い、1 回を残り期限と 60 秒の短い方に制限する。制御が戻ったら期限を再評価する。進捗、結果到着、生存は別の信号として扱う。
- 長いモデル呼び出しはハングと断定せず、制御復帰時の超過として記録する。

## 打ち切り

- 順序は新規調査終了 → 特定した委譲への停止要求 → 停止確認 → 結果の確定 → save → cleanup とする。期限超過後にユーザーへ継続判断を求めず、取得済み根拠で保存へ進む。遅れて届いた結果を理由に調査を再開しない。
- 残った候補は未検証として整理し、取得済み根拠の範囲で保存へ進む。
- 停止要求を送っただけで停止完了とは扱わない。実行中の委譲が WT を使っている場合は削除しない。
- 停止確認は最大30秒を目安に1回。確認不能なら打ち切り、WTを使うworkerのためcomplete/cleanupを呼ばずfailで残存ID・停止状態・WT/セッション/draftの完全パスを返す。既に保存した限定結果は残すが、停止未確認をcleanup成功にしない。後続の依存作業を起動せず、無期限待機や手動の強制削除もしない。
- 既存の保存拒否条件（HEAD 不一致、destination 変更など）は予算より優先する。拒否時は上書きせず、エラーと保存前 draft の場所を報告する。
- 停止機能が実際には使えなかった場合は例外終了として記録し、時間制御成功とは扱わない。

## 未検証結果

時間切れや未再検証で確認が足りない結果は、検証済み指摘と区別して残す。取得済み根拠の範囲で保存へ進み、未読を解消としない。

- 「指摘なし」は検証済み範囲に限る。読めていない範囲があるのに全体を問題なしとしない。
- 時間切れで再現を実行できなかった実行時の挙動の Critical・High・Medium は【確認推奨】として残し、【検証済み】にしない。
- 未検証候補は active の Severity 件数に入れない。時間が足りないだけの候補を既存の【確認推奨】指摘へ自動昇格させない。既存の根拠を満たす【確認推奨】と【要設計判断】の扱いは維持する。
- 更新時に前回 active 指摘を再検証できなかった場合、`Pending previous findings` に過去 ID、タイトル、元 Severity、検出時 HEAD、前回の内容と根拠、今回未確認の理由を保存する。未再検証の指摘を Resolved にしない。次回更新ではこの節も再検証対象に読み込み、解消確認時だけ Resolved に移し、継続が確認できたら同じ ID で active に戻す。新規 ID は active / pending / resolved 全体を見て衝突を避ける。Review history と既存 Resolved は従来どおり保持する。

各節の必須情報と空欄・省略可能条件は次のとおり。

- `Review coverage` は読んだ範囲、読めなかった範囲、実行検証、未実施の検証、委譲状態と省略・中断理由を持つ。読めなかった範囲・未実施の検証がなければそれぞれ「なし」と書く。省略しない。
- `Unverified candidates` は位置、具体的な疑い、確認済み根拠、不足根拠、次の確認方法を持つ。なければ「なし」と書く。省略しない。
- `Pending previous findings` は過去 ID、タイトル、元 Severity、検出時 HEAD、前回内容と根拠、今回未確認の理由を持つ。該当なしなら省略可。
- `Review timing` はcompleteが候補と同じv2開始/終了UTC・経過秒・waiting_secondsとprovenanceを自動生成する。未観測の待ちはnull。全体予算・調査期限・phase内訳・委譲状態・超過理由はcoverageに残す（委譲なし・超過なしも明示）。save/cleanupは本文確定後のため、payloadのsave_seconds/cleanup_seconds/total_secondsで別に報告する。

Merge recommendation の判定順は次に固定する。

1. 検証済み Critical / High があれば `Request changes`。
2. それ以外で重要な未検証候補、未再検証の過去指摘、必要な検証の未実施、差分の実質的な未読箇所があれば `Needs manual verification`。
3. 以上に該当せず従来の基準を満たす場合だけ `Approve`。

補助委譲を省略・中断しただけで、本体が必要範囲を確認済みなら判定を悪化させない。件数表は引き続き active findings のみで計算する。Decided findings（判断の記録で対応しないと判断済みの指摘）は件数・判定に数えない。

時間切れでもHEAD/fingerprint検査を飛ばさない。停止確認不能でworkerがWTを使う場合はcomplete/cleanupを呼ばず、通常入口のfailで停止状態・残存パスを返す。helperの拒否も手で代行しない。最終JSONへsave/cleanup結果と実測を載せ、保存済みレビューを後から直接書き換えない。

## 計測

時間の主張は、全ランタイム共通の phase 時刻を一次情報とする。Claude JSONL を使う暫定分析は、この節の 8 手順に限定する。

1. 開始 UTC、調査期限、委譲起動・停止要求・確認、保存、cleanup の各 phase 時刻を進捗記録に残し、時間の主張はこの記録に基づく。自己報告の phase とトランスクリプト推定値を区別し、混ぜない。
2. Claude JSONL の分析対象は、明示した当該セッションファイルだけとする。親セッションの対象サブエージェントのセッションファイルも正当な入力とする。抽出できる項目は timestamp、type、subtype、durationMs、tool_use の ID と name、tool_result の対応 ID に限定する。message の 本文、tool input、tool result content、thinking は出力しない。
3. 次の jq フィルターは抽出の例であり、ツール実時間を計算するスクリプトではない。

```jq
{
  timestamp,
  type,
  subtype,
  durationMs,
  tools: [
    .message.content[]?
    | objects
    | select(.type == "tool_use" or .type == "tool_result")
    | {type, id, name, tool_use_id}
  ]
}
```

4. `turn_duration` の `durationMs` はターン実時間として列挙できる。ただし区間 `[イベント時刻 − durationMs, イベント時刻]` の重複は統合し、ログ全体の区間へ切り詰める。ターン内のイベント間隔は「モデル応答までの観測間隔」と表記し、思考・生成・サーバー待ちを分離した実測とは呼ばない。
5. `tool_use` と `tool_result` の ID を対応付けても、その区間を実行時間とは断定しない。コマンド自身の elapsed がなければツール実時間は不明とする。0 秒やモデル時間 100% とはしない。
6. ログ全体の区間から親ターン区間の和集合を引いた残りは「ターン外時間」と呼ぶ。ユーザー入力イベント等で裏付けられた区間だけ返信待ちと呼び、親のターン外時間を一律にユーザー待ちとは呼ばない。親と子の時間は別表にし、並行した区間を総時間へ加算しない。割合を示すときは分母を記載する。
7. 欠損、壊れた行、未完の末尾行、時刻欠損、負の duration、順序逆転は件数と影響を示し、推測で埋めない。壊れた JSONL 行を無言で捨てず、解析失敗と影響を記す。`turn_duration` がないランタイムでは phase 時刻のみ報告する。
8. 実測ゲートは、委譲の起動条件を満たすランタイムでの次回の委譲適格レビューで確認する。委譲経過 600 秒以下かつ全体 2700 秒以下、無進捗打ち切り時は最後の実質進捗から停止まで 300 秒以下を満たすこと。全体時間は最初と最後のイベント時刻の差とする。この 300 秒は最後の実質進捗から停止要求までを測り、停止確認の試み（最大 30 秒目安）は別に記録する。予算超過は隠さず、超過箇所と最後の完了条件の未達を記録する。save/cleanup は本文確定後のため、その実測と全体時間は最終応答で報告する。

## 検証シナリオ

次の表は、この共通参照の各分岐が期待どおりに辿れることを確認するためのものである。実行者はスキル本文の各分岐を辿り、期待と根拠箇所を作業記録へ残す。時間を進めた机上検証で実際に 45 分待たない。LLM の行動検証を行う場合も完了したと偽らず、実施した方式と結果を記録する。

| ID | 入力・状況 | 期待 |
| --- | --- | --- |
| S1 | 通常変更 300 行、3 ファイル | 本体のみ。閾値を含む |
| S2 | 301 行 / 3 ファイル、または 300 行 / 4 ファイル | 委譲候補だが、独立範囲と本体の並行作業が無ければ省略 |
| S3 | 10 行 / 1 ファイルでもデータ削除経路、バイナリ、規模不明 | 行数だけで軽量判定しない。必要範囲を本体で確認 |
| S4 | 独立範囲あり、停止・停止確認ツールなし | 起動せず省略理由を記録 |
| S5 | 調査期限まで 9 分 | 新規委譲なし |
| S6 | 起動可能、独立範囲あり、本体精読前 | 最大 1 件起動し、本体精読と重ねる |
| S7 | 起動から 5 分、実質進捗なし。heartbeat は届く | 無進捗期限で停止。ハングと断定しない |
| S8 | 9 分まで毎分実質進捗あり、起動から 10 分 | 絶対期限で停止。延長・再委譲なし |
| S9 | 全体開始から 40 分、未確認候補が残る | 新規調査停止、未検証節へ整理、保存へ移行 |
| S10 | 停止要求後、30 秒の確認でも停止不明 | 不明と報告。保存条件を満たせば限定結果を保存、WT を残す。待機終了 |
| S11 | H-1 は前回 active、今回未再検証 | pending に元 ID・検出時 HEAD・内容を保持、Approve / Resolved にしない |
| S12 | 次回 H-1 の継続または解消を確認 | 同じ ID で active または Resolved へ。新規指摘と ID 衝突なし |
| S13 | 検証済み High と未検証候補がある | Request changes。High なしで重要な未検証があれば Needs manual verification |
| S14 | 補助委譲が中断したが本体の必要範囲確認は完了 | 他の条件を満たせば Approve 可。停止だけで判定を悪化させない |
| S15 | 保存前 HEAD 変更 / API 失敗 / destination 変更 | 履歴追記・上書き・cleanup をしない。既存の拒否条件を維持 |
| S16 | 親 20 分、子 10 分が親の区間内で並行 | 総時間 20 分。30 分にしない |
| S17 | tool_use/result が同時記録、コマンド elapsed なし | ツール実時間は不明。0 秒やモデル時間 100% としない |
| S18 | 単一モデル呼び出し中に期限超過し、復帰時は 48 分 | 復帰後に新規調査せず保存へ。48 分以上の実測を記録し予算未達 |
| S19 | 停止後に遅れて補助結果が届く | 調査や保存を再開しない |
| S20 | verify-devenv.sh または実装担当が生存したまま無進捗 | PR レビュー例外を適用しない。通常の監視規約に従う |
| S21 | 明示予算 20 分、途中でターンを跨ぐ | 開始 15 分で調査終了、20 分全体。起点をリセットしない |
| S22 | JSONL の末尾未完、turn_duration 欠損、時刻逆転 | 解析限界を明示。推測で時刻や分類を補わない |
