# 指摘の根拠と判断の記録の規約

この文書は、レビュアーが指摘の根拠をどう集めて書くか、判断の記録をどう読んで扱うかの手順である。欄のラベル・値・必須の条件と、判断の記録の意味は、形式の定義元 `.agents/review-records.md`（review-records v1/v2）が定める。この文書と形式の定義元が食い違う場合は、形式の定義元に従う。

- 欄の定義: 形式の定義元 4 章（とくに 4.2 節の表）
- D1 の判定に使う材料: 5 章
- 判断の記録の意味と読む側の扱い: 6 章・8.1〜8.3 節

## 1. 実行した再現

### 1.1 いつ必要か

- 実行時の挙動についての Critical・High・Medium は、最小再現を実行してから【検証済み】にする。コードを読んだだけの裏付けでは【確認推奨】にする。
- それ以外の指摘も、挙動が不確かなら実行して確かめる。
- 文書・コメント・静的な指摘（型注釈、命名、依存の宣言など）は `再現: 該当なし`。

### 1.2 どこで実行するか

`$WT` の中にファイルを作らない。再現は次のどれかで行う。

- `$WT` のコードを一時ディレクトリから読み込む（例: `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$WT" uv run --no-project python "$SCRATCH/repro.py"`、`cd "$SCRATCH" && PYTHONDONTWRITEBYTECODE=1 uv run --no-project python -c '…'`）。`PYTHONDONTWRITEBYTECODE=1` が無いと、import したモジュールのバイトコードが `$WT` の `__pycache__/` に書かれる。
- `mkdir -p "$SCRATCH/tree" && git -C "$WT" archive HEAD | tar -x -C "$SCRATCH/tree"` で一時ディレクトリへ展開し、そこで実行する。新しい作業環境（仮想環境の無いディレクトリなど）を作るときもこの形にする。
- 既存のテストは、`$WT` を cwd にして読み取りだけで実行できるものに限り、キャッシュを書かない指定を付ける。`-p no:cacheprovider` が止めるのは `.pytest_cache` だけなので、`__pycache__/` を止める `PYTHONDONTWRITEBYTECODE=1` と併用する。テストの実行方法はリポジトリの規約に従う（素の `python3` には pytest が無いことがある）。親リポジトリでの例: `PYTHONDONTWRITEBYTECODE=1 uv run --project "$TOPLEVEL/tools/devenv" --no-sync pytest -c tools/devenv/pyproject.toml --rootdir . -p no:cacheprovider <テストのパス> -q`（cwd は `$WT`。`--rootdir .` が無いと、テストのファイルを並べたときに別の conftest の同名の fixture を受け取る）。

一時ファイルは、SKILL.md の規約どおり `uv run --no-project python "$TOPLEVEL/.agents/scripts/agent_tmp.py" mkdir "pr-review-scratch-${PR_NUMBER}"` で作る追加スクラッチ（親の main worktree の `tmp/agents/pr-review-scratch-<PR番号>.*`）に置く。証跡はレビュー本文の `再現` に転記し、スクラッチだけに残さない。一時ホームが要る場合は `env HOME="$tmpdir" …` のワンショットだけを使う。

### 1.3 どう書くか

`再現: 実行した` の下に、次の 4 つを書く。

```markdown
- 再現: 実行した
  - コマンド: `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$WT" uv run --no-project python -m tasks.cli import "$SCRATCH/bom.csv"`
  - 場所: 追加スクラッチ（表計算ソフトが書き出す形の、BOM 付きの UTF-8 の CSV `bom.csv` を置いた）。コードは PR head の `$WT`
  - 条件: README の手順どおりに、表計算ソフトで書き出した CSV を取り込む
  - 結果: 終了コード 1、`KeyError: 'title'`（最初の列名が `\ufefftitle` として読まれる）。1 件も取り込まれない
```

- `場所` は、PR head の隔離 worktree（`$WT`）か一時ディレクトリと、そこに置いたもの。
- `結果` は、終了コードと出力の要点。長い出力は要点だけを引用する。
- 実行できなかった、または再現しなかったときは `再現: 実行しなかった（<理由>）` と書き、確度を【確認推奨】にする。理由には、足りないもの（環境・権限・時間・入力）を具体的に書く。推論を再現として書かない。

## 2. 入力・環境の変化

PR が次のどちらかを含むときは、少なくとも 1 つの変化を試す。

- 外部からの入力を受け付けるコード: エージェントの出力、利用者の文章、ファイル、環境変数、コマンドの引数、他のプログラムの出力
- 新しい作業環境で動くコード: 新しい worktree・clone、サブプロセス、一時ディレクトリ、別のユーザー・ホーム

試す変化の例（PR の入力と環境に合うものを選ぶ）:

| 対象 | 変化の例 |
| --- | --- |
| 文章・本文 | 複数行、空、空白だけ、非 ASCII、とても長い、区切り文字（`=`・`,`・`:`・`#`・引用符）を含む |
| パス | 空白を含む、相対・絶対、存在しない、シンボリックリンク、`..` を含む |
| 作業環境 | 仮想環境の無いディレクトリ、依存を入れていない clone、submodule の未初期化・別 commit の状態、読み取り専用 |
| 外部コマンド | 出力が空、終了コードが 0 以外、想定と違う版 |

試した結果は、Review coverage の「実行した確認」に書く（4 章）。試せなかったときは「未実施の検証」に、試せなかった変化と理由を書く。

### 同じ種類の別の入力

欠陥を 1 つ確かめたら、報告された入力の形ではなく、守るべき性質から、同じ性質に反しうる別の入力を挙げて実行する（Issue #547。部分的な修正で同じ種類の入力が残るのを防ぐ）。

- 同じ文法の別の書き方: 例「日時の文字列を、タイムゾーン付きの値として解釈する」なら、`Z` 付きだけでなく、`+09:00` 付き、オフセット無し、小数秒付き
- 同じ状態の別の値: 例「保存に失敗したとき一時ファイルを消す」なら、書き込みの失敗だけでなく、置き換えの失敗の後、中断（Ctrl-C）の後
- 境界の値: 空、1 件、上限ちょうど

結果は候補一覧の `variants` に、入力・結果（反する `violates`・反しない `holds`・未確認 `unchecked`）・確かめた方法を書く。確かめなかった入力も、理由を付けて `unchecked` で残す。

## 3. 「安全か」と「動くか」

- 拒否・停止の挙動を確かめたこと（安全か）は、通常の利用経路で目的の操作が完了すること（動くか）の根拠にならない。両方を別々に確かめる。
- 「失敗時は安全側（停止側）に倒れる」「最悪でも止まるだけ」を理由に、実環境で確かめていない挙動を問題なしとしない。正しい入力まで拒否して止まるなら、それは機能停止である。
- docstring・コメント・PR の説明にある「安全」「同じ規則」「同等」などの主張は、確かめる対象であり、根拠ではない。

## 4. 実行した確認の書き方

Review coverage の「実行した確認」に、入口ごとに 1 行で書く。

```markdown
- 実行した確認:
  - `tasks.cli import`: BOM の無い CSV → 動く（終了コード 0、3 件を取り込む）
  - `tasks.cli import`: 表計算ソフトが書き出した BOM 付きの CSV → 止まる（終了コード 1、`KeyError: 'title'`。H-1）
  - `tasks.cli import`: 列名の無い空の CSV → 止まる（終了コード 2、`missing header`。意図どおりの拒否）
```

- 「動く」「止まる」のどちらかを必ず書き、期待どおりかどうかを括弧の中に書く。
- 動くかを確かめていない入口は、ここに書かず「未実施の検証」に書く。

## 5. 同種箇所の検索

欠陥を 1 つ確かめたら、同じ原因の箇所を探して 1 件の指摘にまとめる。

1. 守るべき性質を 1 文にする。例: 「日時の文字列は、タイムゾーン付きの値として解釈する」。
2. 範囲を決める。prepare の固定baseからreviewed_headまでの全ファイル（`git -C "$WT" diff --name-only "$BASE..$REVIEWED_HEAD"`）。live PRやcommit単体diffを混ぜない。
3. 欠陥の形から検索のパターンを作り、検索する。例: `git -C "$WT" grep -n 'fromisoformat(' -- src tests`、`rg -n 'fromisoformat\(' "$WT/src"`。呼び出し名・定数・正規表現など、原因の形で探す。
   `検索` には実際に実行したコマンドを書く。実行できなかったときは、そのことと理由を書き、実行していないコマンドを書かない。
4. 見つかった箇所を 1 つずつ確かめ、同じ欠陥のものだけを `同種箇所` の `結果` に並べる。同じ形でも正しいもの（例: 直後に `.replace(tzinfo=UTC)` で補っている箇所）は含めない。
5. base に既にある同じパターンは、PR がその経路を初めて使う（顕在化させる）場合だけ含め、そのことを書く。

```markdown
- 同種箇所: 性質「日時の文字列は、タイムゾーン付きの値として解釈する」／範囲 PR の差分（`src/schedule/*.py`・`tests/test_schedule.py`）／検索 `rg -n 'fromisoformat\(' src tests`／結果 `src/schedule/import.py:41`、`src/schedule/export.py:18`、`src/schedule/remind.py:77`。`src/schedule/clock.py:12` は直後に UTC を補っており該当しない
```

- 同じ原因の箇所を、別の指摘に分けない。位置の欄にも全箇所を並べる。
- 原因が繰り返しうるパターンでない（その場限りの誤り）ときは、`同種箇所: 該当なし（<理由>）`。
- 同種箇所（同じ原因のコード上の場所）の検索とは別に、同じ性質に反しうる入力の種類を挙げて確かめ、`variants` に書く（2 章の「同じ種類の別の入力」）。同種箇所を検索しただけで、入力の種類を確かめたことにしない。

## 6. 前回の修正の範囲と重点確認

### 6.1 範囲の求め方

| 状況 | 起点 | `前回の修正との関係` の欄 |
| --- | --- | --- |
| 判断の記録に前のサイクルがある | 最後のサイクルの `reviewed_head` | 全指摘に書く |
| 判断の記録が無く、`$PREVIOUS_REVIEW` がある | `$PREVIOUS_REVIEW` の Review history の最後の行の HEAD | 書かない。確かめた結果は根拠と Review coverage に書く |
| どちらも無い | 範囲なし（初回） | 書かない |

```bash
git -C "$WT" merge-base --is-ancestor "<起点>" "$REVIEWED_HEAD"
git -C "$WT" log --first-parent --no-merges --format='%h %s' "<起点>..$REVIEWED_HEAD"
git -C "$WT" show --stat <範囲の各 commit>
```

- 範囲は、起点から現在のreviewed commitまでのfirst-parentのmergeでないcommit。サイクル間にbaseを取り込んだmergeの変更は含めない。
- 最後のサイクルの `outcome` が `fixes_pushed` なら、その `commit` が範囲にあることも確かめる。
- 起点のobjectが無い、またはreviewed commitの祖先でない場合は範囲を求めず、`前回の修正との関係: 不明` と理由をcoverageへ書く。rebase/force-push後にobjectだけ残っていても、祖先でない起点からの範囲はPR全体やbaseのcommitを含みうるため代用しない。
- 範囲は、重点的に確かめる箇所を決めるためにだけ使う。指摘の対象は PR 全体差分のままで、範囲の外の欠陥も従来どおり報告する。範囲の commit の差分だけを読んで、PR 全体を読んだことにしない。

### 6.2 重点的に確かめること

範囲の変更が新しく足した次のものを、ほかより先に確かめる。

- **仕組み**: 新しい検査・キャッシュ・一時ファイル・ロック・許可リスト・拒否条件。その仕組みが正しい入力を拒否しないか（動くか）、拒否すべき入力を通さないか（安全か）を、両方の入力で実行して確かめる。
- **規則の写し**: 既存の判定を別の場所へ写したもの。写し元と写し先に同じ入力（境界の値を含む）を与えて、結果が一致するかを比べる。
- **「同じ規則」「同等」「同じ判定」の主張**: docstring・コメント・PR の説明・commit message にある主張。主張の位置を書き、実行して確かめた結果を書く。
- **条件の変更**: 範囲の変更が、受け付ける・拒否する状態や、動く・止まる条件を変えたとき、その条件を述べている README・一本化したSKILL.mdとruntime固有の説明・`interfaces.rst`・ヘルプを検索し（例: `rg -n '<条件を表す語>' README.md .agents .claude .devin tools`）、新しい条件と一致するかを確かめる。条件を変えた修正が 1 つの文書だけを直し、ほかの文書が古い条件のまま残る食い違いを見落とさない。検索の語は新しい条件の文言だけにせず、範囲の変更が書き換える前の記述の語と、変えた振る舞いに関わる状態・操作・コマンドの名前も使う（同じ条件を別の言い回しで述べた文書は、文言では見つからない）。結果は候補一覧の `statement_sites` に書き、食い違い（`inconsistent`）は指摘にする。

### 6.3 欄の値

| 値 | 使う場面 |
| --- | --- |
| `該当なし` | 範囲の commit が、この指摘の箇所に触れていない |
| `前回の修正が足した仕組み` | 範囲の commit が足した仕組み・拒否条件の欠陥 |
| `規則の写し` | 範囲の commit が写した規則が、写し元と食い違う。写し元と、一致を確かめた方法を書く |
| `「同じ規則」の主張` | 範囲の commit の主張が事実と異なる。主張の位置と、確かめた結果を書く |
| `不明` | 範囲を決められない。理由を Review coverage に書く |

## 7. 判断の記録

### 7.1 集約

初回・更新・指定commit・非対話ともprepareが返したrecordsを使う。prepareは同じPRのコメントを全ページ取得して共有parserで集約する。callerは `--records-comments` に同じ形式のローカルcomments JSONも渡せる。別の手順へ分岐せず、同じ判断を適用する。

- `decisions` はsources/state/historyを持つ。`rounds` の最後のサイクルのreviewed_head/outcome/commitは6章の範囲へ使う。
- `decisions` が空なら記録なしとして正常。API失敗・壊れた記録・別PRの記録は記録なしと推測せずfailed。
- `ignored_comments` に挙がったコメントは記録として扱わない。
- 記録は、新しい指摘の候補を探す情報源にしない。他モデルのレビューファイルを読まない規則は変わらない。

### 7.2 状態ごとの扱い

自分の指摘・候補に対応する判断は、判断 ID ではなく `sources` で探す。指摘の参照は `<レビューファイル名>#<指摘 ID>@<検出時 HEAD の先頭 12 桁>` である（形式の定義元 2.1 節）。

| 判断の状態 | 扱い |
| --- | --- |
| `skip`（対応しない） | 同じ問題で新しい根拠（7.3 節）が無ければ active にしない。`## Decided findings` に書き、件数表・重大度・Merge recommendation に数えない。新しい根拠があれば active にし、`見直しの根拠` に判断 ID と新しい根拠を書く |
| `resolved`（解消済み） | 現行 HEAD で再現したら、回帰として active にし、根拠に判断 ID を書く |
| `fix`（対応する） | 前回の修正を確かめる対象にする。`history` の最後の `outcome` が `fixes_pushed` のときだけ、修正済みとして確かめる。解消していなければ active のまま続ける |
| `hold`・`unverified` | 通常どおり扱う。足りない確認を補えたら、根拠に書く |

- Update で、前回 active だった自分の指摘が `skip` になっていて新しい根拠が無ければ、ID・タイトル・検出時 HEAD を保ったまま Decided findings へ移す。
- Initial でも、自分の候補が `skip` の判断と同じ問題で新しい根拠が無ければ、新しい ID を付けて Decided findings に書く。
- 同じ問題かどうか迷うときは、active のまま「判断 `<判断 ID>` と同じ可能性がある」と書き、planner に任せる。

```markdown
## Decided findings

### L-2: 取り込みの一時ファイルを、失敗したときに消さない

- 判断: `claude-opus-5-5#L-2@0123456789ab`（対応しない。1回目、planner claude-opus-5-5）
- 位置: `src/tasks/importer.py:58`
- 検出時 HEAD: `0123456789ab`
- 新しい根拠: なし（見直す条件: 一時ファイルが残ることで次の取り込みの結果が変わる再現が出たとき、または利用者が指定したとき）
```

### 7.3 新しい根拠

`skip` の判断を見直してよいのは、次のどれかがあるときだけである（形式の定義元 8.2 節）。

- 記録に無い、実行した再現
- 記録の判断と異なる利用経路・結果の種類を示す再現
- 指摘の対象のコードが、発生条件を変える形で変わった
- 利用者の指定

表現の違い、別のレビュアーが同じ指摘を出したこと（票の数）、重大度の表記だけの引き上げは、新しい根拠に当たらない。

## 8. D1 の材料

採否（Fix・Skip）は planner が決める。レビュアーは判定の材料を欄に書く。

- `利用経路`: 入口（文書化された操作。CLI・スキルの手順・それらから呼ばれる関数）、入力（普段の利用で生じる入力か）、環境（サポートしている環境が実際に取る状態か）を書く。入口からは渡せない値で内部の関数を直接呼ぶ再現は `限定的`。その環境に無い設定（独自の Git 設定、PATH から仮想環境を外した状態など）が前提なら `限定的`。
- `結果の種類`: 完了すべき操作が失敗する・止まる・正しい入力を拒否するなら `機能停止`、完了しても誤った対象・記録・結果になるなら `誤った結果`。遅いだけ・通知が遅れるだけ・ログが多いだけなら、それ以外の値。
- `PR 起因`: 問題のコードを入れた commit を `git -C "$WT" log -S '<特徴的な文字列>' --oneline` などで探し、base 側の状態を merge-base の `git show <merge-base>:<path>` で確かめる。PR が入れたなら `持ち込み`、base にあったコードを PR が初めて通常の経路で使うなら `顕在化`、PR と無関係に base にあるなら `既存`。要件の実装漏れ（PR が満たすとした受け入れ条件の処理・入口が無い）は `持ち込み` とし、根拠に要件の出所と、処理が無いことを確かめた検索を書く。

## 9. 候補一覧の JSON

レビューファイルと同じ指摘を、候補一覧の JSON にも書く（SKILL.md の「候補一覧と実行情報」の節）。項目と値は [review-findings](../../../review-findings.md) の 4 章にあり、レビューファイルの欄との対応は 3 章にある。

| レビューファイル | 候補一覧 |
| --- | --- |
| 見出しの ID・タイトル・確度ラベル | `id`・`title`・`confidence` |
| 節（Critical〜Info） | `severity` |
| `位置`・`検出時 HEAD` | `locations`（`位置` の行に現れる文字列で書く）・`detected_head` |
| `内容` の発生条件 | `failure_scenario`（入口・入力・環境・操作の順番・期待する結果・実際の結果） |
| `同種箇所` の性質 | `property`（同種箇所が `該当なし` でも書く） |
| 2 章の「同じ種類の別の入力」の結果 | `variants` |
| 6.2 節の「条件の変更」と、SKILL.md の「条件を述べる文書との照合」の結果 | `statement_sites` |
