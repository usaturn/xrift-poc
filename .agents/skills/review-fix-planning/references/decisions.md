# 全指摘の採否

## 判定の材料

指摘ごとに以下をSpecへ残す。妥当であることと、このPRで直すことを分ける。

| 項目 | 内容 |
| --- | --- |
| 参照 | `<review file>#<finding ID>@<検出時HEAD>`。別レビュアーの同じIDは別参照 |
| 対象 | repository/PR/現行HEAD/比較したbase commit |
| 妥当性 | 現行で成立、解消確認済み、必要確認が未完了 |
| PRとの関係 | introduced（持ち込み）、surfaced（既存潜在不具合を顕在化）、preexisting、unknown。差分行にあるかだけで決めない |
| 変更種類 | 不具合修正、機能追加、仕様拡張、任意改善 |
| 重大度 | reviewの値、再評価した値、根拠 |
| 採否 | 状態、H/D1/N/明示Holdの基準、理由 |

## Fix・Skipの境界

- H: 現行で成立しPR起因（introduced/surfaced）のCritical/High。安全性再評価も同じ条件。
- D1: 下記の4条件全部。重大度のラベルにかかわらず必須Fix。
- N: 利用者がこのPRでこの指摘を名指し。理由・範囲・検証を残し、必須Fixとは別にする。「レビュー対応して」「進めて」はNではない。
- それ以外はSkipが既定。Medium/Low/InfoはD1/N/根拠ある安全性High以外に採用しない。「小さい」「文書だけ」「テスト1個」「複数モデルの指摘」は理由にならない。
- 機能、仕様拡張、将来対策、任意改善は重大度を問わずSkip、必要なら別Issue/PR候補。通常の実装委任を範囲拡大の認可にしない。
- 意図する挙動の質問はSkip、Specへ質問を一行。Holdにせず、通常判断の質問待ちにしない。
- first-party経路が一貫し、third-party theme/downstreamだけの互換性ならSkip。repository方針で決着した質問もその方針を引用してSkip。
- 誤った記述、回帰防止テストの撤去だけでは採用条件を満たさない。影響をH/D1/Hold/Skipで判定する。
- 既存不具合は現在再現してもHのFixではない。既存Critical/Highを「範囲外」で隠さず、影響・持ち越し先・人による要確認をSpec/状況コメント/会話に残す。
- Skipの持ち越しは既存Issueを優先。無ければ内容・影響・出典・今回しない理由の一行候補。Issue作成は認可がある場合だけ。持ち越しの失敗で修正ループを延長しない。

## D1の4条件

現行のコミット済みコードで全部確かめる（共有定義は `.agents/review-records.md` 5章）。

1. **実行再現の記録**: reviewerの「再現: 実行した」のコマンド/場所/条件/結果、またはplanner/verifierが隔離環境で実行した記録。一覧がコード・文書を読んだだけなら再現ではない。古いHEADの記録は関連path無変更をgit diffで確認するか再実行する。推論を実行にしない。
2. **通常の利用経路**: 入口・入力・環境が通常利用。文書化された入口、実際に来る入力、対応環境に本当にある設定。
3. **停止か誤結果**: 遅さ、通知の遅延、ログが多いだけは含まない。
4. **PR起因**: introduced/surfaced。

記録の `d1` に再現者・経路・result_kind、planner/verifierなら再現全文を残す。実行記録無しをD1にしない。

## 安全性3項目の重大度再評価

現行のコミット済みコードを読み、通常の入口/入力/環境から次の経路を確認できたら、High未満をHighへ上げる（Criticalは維持）。実行再現は必須でない。

1. 認証情報/秘密が想定外の相手へ渡る（child process、ログ、外部サービス、PRコメント等）。
2. 意図したworktree/target repository/指定directoryの外を書換え・削除する。
3. 権限検査または書込み前検査を回避できる。

入口、入力、環境、漏洩先/書換え先/回避する検査を具体的に示す。通常入口が無検査で受け入れる計画/レビューのパス、READMEが設定する環境変数等は、実際の利用で来る入力として扱う。`../`だから潜在バグ、とHoldへ落とさない。

- Specにreview重大度→High、項目番号、経路を書く。記録のseverityはHigh、reasonには `安全性 <番号>:` と経路。HでFixにしたものだけ `H: 安全性 <番号>:` で始める（runtime共通）。
- PR起因ならHのFix、既存ならSkip（影響・持ち越し・人の要確認）。既存HighのreasonをH:で始めない。
- 経路無しの憶測/将来変更、対応環境に無い設定を必要とするものは再評価しない。元の重大度で判定する。
- 経路を名指したPR起因候補の確認を終えられなければUnverified。確認までseverityは元の値。既存候補の確認不足は元のseverityでSkip、足りない確認と、成立なら既存Highとして要確認になることを残す。
- D1も成立する場合はいずれかの基準でFixにできる。使った基準を記録する。

## Hold・Unverified・Resolved

**Holdだけに事前のhold-actionを適用する。** PR起因、コミット済みコードで確定、数行で除ける潜在バグ、正常経路はまだ壊れないものに限る。未選択は認可不足のstopped、fix選択は追加Fix、skip選択は理由付きSkip。

Holdではない: 低重大度ゆえ不採用の文書/保守/性能、検証未完了、機能/仕様/意図の質問、無関係な既存不具合、安全性3項目（Highで判定）。Skip/Resolved/UnverifiedをHold経由で自動採用しない。

Unverifiedは、足りない事実が採否を変える（成立すればH/D1）場合だけ。Medium/Low/Infoなら、通常経路の停止/誤結果のD1実行再現が終わらない、またはPR起因の安全性3項目の経路確認が終わらない場合。経路が通常外、結果が停止/誤結果以外なら、成立してもSkipなので不足も理由に書いてSkip。

失敗コマンド、環境不足、timeout、未読はResolved/「再現しない」ではない。必要確認は自力で続け、具体的障害が解消できないときだけstoppedにする。Unverifiedを残したno_fix_neededは禁止。Resolvedは現行のコミットで解消を確認した根拠付きだけ。

## 同原因と最小修正

- 同じ問題の複数参照を1判断へまとめ、元IDを全部sourcesに残す。票数を重大度の証拠にしない。
- Fix前に原因・守る性質を言語化し、差分と直接の呼出元/呼出先まで同原因を探す。reviewerの同種箇所は現行で確認。無ければ性質・範囲・検索command・結果を自分で残す。差分外検索はこの範囲だけで、無関係な掃除に広げない。
- 見つけた既存箇所にも同じ採否を適用する。機械的に全箇所Fixにしない。
- 欠陥と回帰だけを取り除く。事前条件を一度検査して止める方法、仕組みの削除/統合/簡素化と新分岐追加を比較する。同じ判断をREADME/skill/scriptへ増殖させず、既存定義元へ揃える。文書すべてのスクリプト化や共有frameworkを作らない。
- reviewerの推奨文・手法は仮説。全violates変種を解消し、holds変種を維持できることを確認する。inconsistentの記述箇所も対象/受け入れ基準へ含める。uncheckedなら理由を残す。
- 「同じ/等価な規則」と主張する実処理は一致する挙動をテストする。拒否を足すなら複数行自由文・submodule状態等、受け入れ続ける実入力もSpec/挙動テストへ入れる。
- テストはAGENTS.mdの採用基準で要否を決める。必要な回帰テストを「差分を小さくするため」に消さない。同種例はparametrizeでまとめる。文面/運用値を写すテストへ代用しない。

## 継承・再指摘

Skipは継承。見直せる新根拠は、記録に無い再現、別経路/結果を示す再現、条件を変えるcode変更、利用者の指示（共有定義8.2章）。言い換え、別reviewer、重大度ラベルだけは新根拠ではない。

前のFixは修正HEADで必ず再確認し、解消ならResolved/changed、残るならFix/inheritedでD1も維持する。Resolvedの再発はchangedの回帰。前の修正が持ち込んだ欠陥は新しいPR起因の判断として扱い、後のサイクルというだけで落とさない。記録済みsourcesを別の判断へ移さず、後から同一と分かれば一方をSkipにして他方のID/再検討条件を記す。
