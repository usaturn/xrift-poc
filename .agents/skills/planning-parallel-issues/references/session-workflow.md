# 子を 1 つ planning の handoff まで進める

## 最新の証拠から選ぶ

入口として親を読み、次に native の子、現在の本文、コメントの全ページ、依存関係、PR の状態、claim ref を取得する。コメントの最初の応答を完全な証拠として扱わない。状態で選ぶ前にページ送りをたどり、GitHub CLI を使う場合は `gh api --paginate` を使う。Issue が close されていることだけでなく、必須の変更が対象 branch に含まれていることを確かめる。既定の選択条件では、各先行 Issue が `state_reason=completed` で close され、必要な PR がマージされている必要がある。`not_planned` と `duplicate` は条件を満たさない。duplicate の先行 Issue はボード上で重複先の Issue に置き換え、選択の前にその Issue を評価する。成果物だけが入力になる先行 Issue には、明示された完了の証拠を求める。早い段階の planning のゲートを使えるのは、ボードがそれを名指ししていて、その必須の入力が確認済みの場合だけである。

claim 済みの子と、有効で復元できる成果物をすでに持つ planning-ready の子は飛ばす。条件を満たす子を 1 つ選ぶ。選ぶときは、ボードの優先順位を使うか、安定した決め手として最も小さい番号を使う。名指しされた planning-ready の子を再開する場合は、その成果物を検証・復元し、重複を作る代わりに、その到達点を報告する。条件を満たす子が無ければ、blocker をそれぞれ報告し、際限なくポーリングしたり claim をため込んだりせずに終える。

[github-operations.md](github-operations.md) に従って所有権を取得し、確かめる。取得の後に、着手の条件を再び確かめる。変わっていたら、自分の claim を解放して評価し直す。リポジトリの方針が求める場合は、経過時間と主な作業の所要時間を記録する。

## ルーチンの承認で止まらずに続ける

求められている到達点は、推奨案を使った **Spec → Plan → agent-handoff** である。インストール済みのこれらのスキルを順に読んで適用する。見出しをまねるだけで済ませない。この手順には、ルーチンの planning の手順を完了させるための利用者の認可が含まれている。推奨案とその根拠は agent の判断として記録し、決して人間の承認として記録しない。設計の提示の時点、Spec の後、writing-plans の実行方式の選択のところで止まらない。

利用者は、すべての子について文書の成果物を明示的に求めている。これは、Spec と Plan を省く、範囲の限られたタスク向けの brainstorming の近道より優先する。既存のコードへの小さな変更でも、brainstorming の Spec を書く経路を使う。文書の詳しさはタスクに合わせ、その後 writing-plans と handoff に進む。求められた文書を正当化するためだけに、単純な変更を複雑なものと分類し直さない。

| 観察できる状態 | 対応 |
|---|---|
| hash 付きの、全文がある既存の Spec・Plan | 正確なバイト列を復元して確かめ、現在の Issue と base に合うかを調べ、有効な部分を再利用する |
| 両立する既定値がある、通常の曖昧さ | 推奨案を選び、代替案と理由を記録して続ける |
| planning の途中で Spec が変わる | Spec とその hash を更新し、その後 Plan と handoff を整合させる |
| 有効な、完了済みの planning の handoff | 復元して確かめる。ファイルを作り直すためだけに brainstorming をやり直さない |
| 必須の入力・認可の不足、または範囲を変える未解決の決定 | 途中の成果物を残し、blocker と具体的な復旧の操作を記録する。進捗を記録した後に、自分の claim を解放する |
| 必須のスキルが無い | インストール済みのスキルを探す。使えなければ、足りない依存を正確に報告し、途中の作業を残す。代わりのものを、そのスキルを実行したと決して表示しない |

既存の成果物の hash が示すのはバイト列が同一であることで、設計が妥当であることではない。受け入れる前に、その決定事項を読み、現在のインターフェースを確かめる。別のエージェントの成果物を引き継ぐ場合は、読む側でも `agent-handoff` を適用する。

## 必須の成果物

パスはリポジトリの規則から決める。Superpowers の既定値は、リポジトリが上書きしていない場合だけ適用する。ignore された下書きのファイルも、remote からの復元が必要である。リンクを機能させるためだけに、ignore された成果物を force-add しない。

1. **Spec:** 目的、範囲と対象外、制約、提案する設計、推奨案を示した代替案、インターフェース、受け入れ基準、依存関係の証拠、決定した曖昧な点。`superpowers:brainstorming` を、そのレビューの手順も含めて使う。続行の根拠となる権限を正確に記す。
2. **Plan:** `superpowers:writing-plans` を、そのレビューも含めて使う。実際の Spec にリンクし、正確なファイル、タスクの順序、インターフェースの詳細、期待する結果を伴う意味のある検証、反映の制約を書く。子の担当範囲と前提のゲートを保つ。実装とテストのコマンドは将来の指示であり、実行したという主張ではない。リポジトリの contingency の要件に従う。
3. **handoff の対:** `agent-handoff` とそのインストール済みのスキーマを使う。親の main worktree（`uv run --no-project python .agents/scripts/agent_tmp.py root` が出力するディレクトリ）の下に、`tmp/docs_draft/claude_handoffs/<timestamp>-<session>.handoff.md` と、対になる `.handoff.json` を、同じ事実で書く。Schema v2 で必須なのは、`schema_version`、`generated_at`、`project_dir`、`session.id/stop_reason`、`decisions`、`out_of_scope`、`verification.commands/isolation`、`landing.branch/pr/prohibited`、`git.worktree/branch/head/status`、`sources.spec` である。`sources.plan` と次の操作も含める。誤って親の checkout の情報を書くのではなく、実際の Git の事実を書き入れる。null でないすべての出典のパスが存在することを確かめる。まだ作っていない PR は null とし、許される作成・再利用の方針を書く。
4. **復元の manifest:** ファイルごとに 1 項目を、役割、portable なパス、SHA-256、バイト数、remote の URL・コメント ID、エンコーディングと chunk の順序、成果物の revision、base SHA とともに保存する。元のホストのパスは、来歴としてだけ残す。受け手がそれを新しい checkout にどう対応付け、ホスト固有の handoff の事実をどう作り直すかを説明する。子に投稿する最後の状況コメントから、すべての項目にリンクする。

## 公開し、復元してから解放する

外部への書き込みのたびに、その前に、claim がまだ保存した SHA と一致することを確かめる。認可された Issue のコメントか、リポジトリ上の場所を通して公開する。バイト列をそのまま保つ。小さなファイルは、コードフェンスで全文を載せてよい。任意の内容を確実に扱うには、順序と decode 後のバイト列の hash を付けた base64 の chunk を使う。認証情報や非公開の実行ログを決して公開しない。Spec、Plan、handoff の 2 ファイルを全文で含める。ローカルのパス、要約、SHA だけ、push していない commit は、復元の手段にならない。

ローカルの元のファイルを写さずに、公開した内容を新しい空のディレクトリに取得する。4 つのファイルすべてを decode・再構成し、manifest の hash とバイト数を確かめる。handoff の JSON を parse し、必須のフィールドを確かめ、その事実を Markdown と比べ、portable な出典のパスを再構成した一式の中で解決する。Spec と Plan の整合を確かめる。この往復の後でだけ、`planning: ready`、`implementation: not-started`、manifest へのリンク、実行できる次の手順を公開する。実装の Issue は open のままにする。planning の完了は、後続の実装の依存関係を満たさない。

正確な SHA による lease で解放し、ref が無いことを確かめる。アップロードや往復に失敗した場合は、`planning: incomplete` とし、途中の結果への参照と復旧の操作を残す。進捗を公開した後に、自分の claim だけを解放する。GitHub が使えない場合は、復旧の記録をローカルに保存し、未解放の claim があることを明示して報告する。他者の SHA は、所有権を失ったことを意味する。書き込みを止め、その ref を削除しない。説明の無いまま claim を保持して受け手を待つ状態で、決して終えない。

最終の回答には、子の URL、4 つの成果物の実際のパスと remote の manifest、実際に行った確認、planning と実装の状態、claim の解放の結果、次の操作を含める。Plan や handoff を後で作ると申し出ない。それらはこのタスクの一部である。
