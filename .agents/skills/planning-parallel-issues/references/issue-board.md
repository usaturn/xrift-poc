# 実行できる Issue ボードを作る

## 分割の前に調べる

リポジトリの規則、タスク、関係するコードとテスト、既存の親と子の Issue とそれらのコメントの全ページ、リンクされた PR を読む。実際の対象リポジトリと default branch を特定する。同じ目的の既存のボードがあれば再利用し、その決定事項を残し、無関係な内容もそのまま残す。情報源の URL と、関係する base SHA を記録する。

共有インターフェース、fixture、設定、生成ファイル、検証用のリソースを洗い出す。共有する変更は基盤（foundation）の子にまとめ、後続の子には、重ならないファイルの担当か、重ならないことを正確に示した節を割り当てる。両方の branch が registry を編集せずに統合する方法を明記する。グラフを並行に見せるためだけに、実際の依存関係を外さない。

各子は単独でレビューでき、1 回の実装セッションに収まる大きさでなければならない。子は作業に必要な数だけ作る。最後の統合や計測が複数の branch を使う場合は、別の子に分ける。依存関係とは具体的な入力のことである。その入力の名前と、それが利用できることをどう確かめるかを書く。

子ごとに、直接の先行 Issue の ID を 1 つの基準一覧にまとめる。親の表、子の blocker の一覧、図、辺の数、native の API への書き込みは、すべてこの同じ一覧から作る。推移的な入力は、直接の blocker と分けて書く。たとえば 2 つの exporter を使う CLI は、それらの共有インターフェースも使う。しかし、そのインターフェースがすでに両方の exporter に先行しているなら、native の辺をもう 1 本足すことにはならない。

## 親の本文に必要な項目（この順に書く）

1. **成果と境界:** 測定できる完了基準、対象外、情報源の Issue、現在の base branch と SHA。
2. **実行マップ:** 子へのリンク、目的、担当ファイル、先行 Issue、必要な入力、完了の証拠、planning の状態、実装の状態。snapshot を確認した時点を書く。claim と状態の判断の根拠は、取得し直した子のデータに置く。
3. **Publication ledger:** 親の本文の中の管理対象の節。固定のボードキーと、子ごとに、固定の子キー、Issue の `number`、データベースの `id`、`node_id`、`html_url`、所属すべき親を書く。管理対象の依存関係の両端を、固定のキーとデータベースの ID で記録する。付け替え（reparent）が終わっていない間は、正確な再取得で移動を確かめるまで、確認済みの置き換え前の親の `number`、データベースの `id`、操作の状態を残す。後のセッションが基準とするのは、この公開された節である。ローカルの ledger は、公開前の写しにすぎない。
4. **依存関係の DAG と並行の wave:** 基盤、独立したレーン、統合。native の `blocked_by` は図と一致させる。同時に実行できない検証用のリソースがあれば、共有のロックの場所と担当者を含めて書く。
5. **共有インターフェースと担当:** 凍結したシグネチャと成果物、担当の子、利用する側、子をまたいで禁止する編集、統合の担当者。2 つの子が 1 つのファイルを編集する場合は、重ならない節を示すか、その編集を 1 つの担当にまとめる。
6. **運用規則:** 着手の条件、claim の名前空間、必要なアクセス権と確認済みのリポジトリの制約、解放、成果物の保存と復元、planning-ready と実装済みの区別。親の snapshot は coordinator が更新する。子のセッションは自分の子に状態を公開し、親の本文全体を同時に書き換えることを避ける。
7. **開始指示:** 下のブロックを省略せずに貼り、リポジトリ固有の選択を実際の値に置き換える。読む側が、それまでの会話も、このスキルのインストール済みの写しも無しに、子を特定して引き受けられるようにする。

### 親に入れる開始指示

言語は利用者に合わせる。リポジトリ、default branch、成果物の置き場所、検証のコマンド、スキルの場所は、このリポジトリから決める。公開する本文に、未解決のプレースホルダーを残さない。

> この親から子を 1 つ始め、このセッションでその子の planning の handoff まで終える。
>
> 1. リポジトリの規則、Publication ledger を含むこの親、native の Sub Issue の全ページ、各候補の最新の本文、各候補のコメントと `blocked_by` の関係の全ページ、必須の PR、`refs/heads/agent-claims/issue-N` を読む。ページ分割されるどの集合についても、最初の応答を完全な証拠として扱わない。状態で選ぶ前にページ送りをたどり、GitHub CLI を使う場合は `gh api --paginate` を使う。表は snapshot である。open の子を 1 つ選んでよいのは、必須の先行 Issue がそれぞれ `state_reason=completed` で close され、必須の PR が対象 branch にマージされ、必要なインターフェースと成果物が利用できる場合だけである。`not_planned` と `duplicate` は依存関係を満たさない。duplicate の先行 Issue はボード上で重複先の Issue に置き換え、選択の前にその Issue を評価する。成果物だけが入力になる先行 Issue には、記載された成果物が確認済みであることを求める。このボードが早い段階の planning のゲートを別に定めている場合は、そこで名指しされた証拠を確かめる。その場合も実装の依存関係は適用される。既存の claim があれば、古いものも含めて、その子を除外する。有効な planning の handoff がすでにある子は、明示的にそれを再開する場合でない限り飛ばす。条件を満たす子が無ければ、blocker を列挙し、claim せずに終える。
> 2. その子だけを claim する。現在の Issue の書き込み権限と repository contents の書き込み権限、適用される ref の rulesets、workflow の branch の filter を確かめる。このセッションが、ボードに記録された制約の下で、claim ref を作成・読み取り・条件付きで削除できなければならない。エンドポイントが、rulesets や branch protection はリポジトリのプランでは利用できないと明示している場合は、そのエンドポイントと応答を、この仕組みによる制限が適用されないことの証拠として記録し、ほかの権限・workflow の確認と、claim の操作ができるかどうかの確認を続ける。権限の拒否による、またはそれ以外の理由で判断できない `403`/`404` は、未確認のままとして扱い、claim の取得を止める。このプロトコルが使えない場合は、claim を取得せずに具体的な blocker を報告する。対象 branch の最新の tree と parent を使い、message に Issue 番号、session UUID、UTC 時刻を含めた一意の空の Git commit を作る。得られた SHA を保存する。その SHA を指す新しい Git ref `refs/heads/agent-claims/issue-N` を、アトミックに POST する。共有の base SHA への通常の push、assign、コメントでは足りない。失敗したとき、または応答が不確かなときは、ref を GET する。所有を証明するのは、自分が保存した SHA だけである。別の SHA なら別の所有者であり、2 日間動きが無くてもそれは変わらない。ref を force-update したり、古さを理由に横取りしたりは決してしない。所有者、セッション、ref、SHA、目的を子に記録する。
> 3. claim の後と外部への書き込みの前に、ref と着手の条件を確かめ直す。tracked な作業には、隔離した worktree を使う。既存の Spec・Plan・handoff の成果物は、公開された内容から復元し、再利用の前に SHA-256 を確かめる。前の作業を引き継ぐときは `agent-handoff` を読む。成果物のローカルのパスをこのホストのものに読み替え、元の hash を記録する。
> 4. Spec の作成または検証に `superpowers:brainstorming`、Plan の仕上げに `superpowers:writing-plans`、`.handoff.md` と schema version 2 の `.handoff.json` の両方の作成に `agent-handoff` を使う。利用者が文書の成果物を求めていることは、範囲の限られたタスクでは Spec も Plan も作らないという brainstorming の近道より優先する。小さな変更でも Spec を書く経路を使い、詳しさはその大きさに合わせる。成果物のパスはリポジトリの規則に従う。通常の曖昧さには推奨の既定値を当て、理由と代替案を agent の判断として記録し、ルーチンの確認や実行方式の選択で止まらずに続ける。人間の承認を決して作り上げない。本当に足りない認可、利用できない必須の入力、範囲を変える未解決の決定は、blocker として記録し、完了した作業を残す。
> 5. handoff の 2 ファイルで、決定と処置（decisions/dispositions）、対象外、正確な検証のコマンドと隔離、反映先の branch・PR・禁止する操作、実際の worktree・branch・HEAD・status、Spec と Plan の出典、次の操作を一致させる。必須のフィールドと、null でないパスが実在することを、インストール済みの `agent-handoff` のスキーマに照らして確かめる。この planning のタスクの間は、実装を実行せず、そのテストが合格したと報告しない。
> 6. Spec、Plan、handoff の 2 ファイルを、正確に復元できる内容として、子の中か、認可されたリポジトリ上の場所に公開する。成果物の役割、portable なパス、SHA-256、バイト数、出典の URL・コメント ID、エンコーディングと chunk の順序、revision・base SHA、planning の状態を列挙した manifest を公開する。サイズの上限に対しては、UTF-8 として安全な境界で分割するか、base64 の chunk で保存する。参照や要約だけでは足りない。remote の写しだけを新しいディレクトリに取得し、バイト列を組み立て直し、すべての hash を確かめ、JSON を parse し、Spec・Plan・handoff の整合を確かめる。権限や取得に失敗した場合、planning は未完了のままである。ローカルの結果と、復元の正確なエラーを残す。
> 7. 子に `planning: ready`、`implementation: not-started`、manifest の URL、次の操作を公開する。実装の Issue は open のままにする。変更しない（immutable な）claim を解放するのは、それがまだ自分の SHA と一致する場合だけで、`git push --force-with-lease=refs/heads/agent-claims/issue-N:CLAIM_SHA origin :refs/heads/agent-claims/issue-N` を使う。ref が無くなったことを確かめる。SHA が違う場合は削除せず、所有権を失ったことを報告する。止まった場合は、自分の claim を解放する前に、途中の進捗と復旧の操作を公開する。次のエージェントを待つ間、claim を保持しない。実際の成果物と残りの作業を報告し、親の snapshot の更新は coordinator に任せる。

## 子の本文に必要な項目

| 項目 | 具体的な内容 |
|---|---|
| 親と目的 | 親へのリンク。観察できる結果 1 つ |
| 範囲と対象外 | 許可する編集と禁止する編集を別々の一覧にし、どのパスも両方には入れない。担当ファイルは親の表と一致させる |
| 依存関係 | 先行 Issue へのリンク、正確な入力と証拠、既定の完了条件。早い段階の planning のゲートがあれば、明示する |
| インターフェース | 入力と出力、エラー、凍結したシグネチャとその担当 |
| 受け入れ | 観察できる振る舞いと、回帰・検出に関する制約 |
| 検証 | 正確なコマンド、作業ディレクトリ、必要なサービスとデータ、隔離とロック |
| 成果物 | Spec、Plan、handoff の対、復元の manifest。必要なら最終的な実装の PR |
| 状態と反映 | planning と実装を分けた状態、親から引き継ぐ claim のプロトコル、対象 branch、PR の再利用・作成の方針 |

## 分割の例

CSV/JSON の export では、次のグラフにする。

```text
Interface and registry ─┬─ CSV exporter ──┬─ CLI integration
                        └─ JSON exporter ─┘
```

基準となる直接の先行 Issue は `interface: []`、`csv: [interface]`、`json: [interface]`、`cli: [csv, json]` で、辺はちょうど 4 本である。CLI が推移的に使うインターフェースは入力として書き、5 本目の `blocked_by` の辺にはしない。

基盤は `app/export_registry.py` と `tests/test_export_registry.py` を担当する。中身は request/result のインターフェースと、exporter の担当者が後から編集しなくてよい登録の仕組みである。CSV は `app/csv_export.py` とそのテストを、JSON は `app/json_export.py` とそのテストを担当する。統合は `app/cli.py` と `tests/test_cli_export.py` を担当し、exporter を import して、凍結した API で登録する。exporter の 2 つの子が両方とも registry を編集することは、決してしない。検証のコマンドは実際のプロジェクトから取る。依存関係の完了には、親のチェックボックスに印が付いていることではなく、凍結したインターフェースが対象 branch で利用できることが必要である。

## 公開と確認

公開の前に、すべての子の許可・禁止のファイル一覧を、親の担当の表と照らし合わせる。テストや登録を含め、予定する編集にはそれぞれ担当が必要である。どの子も、自分に割り当てられたファイルを禁止したり、兄弟の子のファイルを断りなく編集したりしてはならない。節をまたぐ矛盾は、GitHub に書き込む前に直す。

[github-operations.md](github-operations.md) を使う。Issue への書き込みのたびに、返った ID と URL を親の本文の Publication ledger に保存し、セッションをまたいでそれらの値に頼る前に読み戻す。子への実際のリンクを書き入れ、native の Sub Issue と依存関係を、別に手で数えた数ではなく、先行 Issue の基準一覧と突き合わせる。追加・削除・付け替えをするのは、公開された ledger と現在の Issue の本文によって管理対象と証明された関係だけである。`replace_parent: true` を使う直前に、子の native の親を読み、そのデータベースの ID が、同じボードの確認済みの置き換え前の親と一致することを使う条件とする。読み取れる子が代わりに 404 `No parent issue found` を返した場合は、`replace_parent` を付けずに所属すべき親へ追加する。読み取れない、または不明な現在の親との関係はそのまま残し、ボードを未完成のままにする。付け替えや追加の結果が不確かな場合は、再試行や成功の宣言の前に、子の親と、関係する旧親・新親の子の一覧の全ページを取得し直す。変更の後は関係の全ページを取得し直し、管理対象の辺の集合を基準のグラフと比べる。担当の一覧、ledger、本文も比べる。循環と子の重複を確かめる。公開した開始指示とリンク先のすべての入力は、想定するエージェントが参照できなければならない。

API のエラーが起きると、ボードは途中まで準備された状態で残る。どの関係やフィールドが欠けているかを正確に報告し、保存した ID から再開する。そのボードを ready として告知したり、native の依存関係を断りなく文章による記述に格下げしたりしない。既存のボードの更新は、現在の本文とコメントの全ページを読み直したうえで、管理対象の節に範囲を絞って行う編集である。別の作成者による無関係な変更を決して上書きしない。
