# 作業中に判明した範囲外の不具合の記録

PR の作業（実装・検証・レビュー修正・CI の待機・マージ）の途中で、その PR の範囲の外にある不具合が判明したときに、どこへどの形で書くかを定める。記録は `review-carry-over-followup` が持ち越し候補と同じ調査・重要性の判断に通す（同スキルの手順 1）。記録する側は起票するかを決めない。

## 対象

- その PR の変更が原因ではなく、Issue の受け入れ条件にも含まれない不具合で、コードを読むか実行して確かめたもの。例: 検証の失敗の原因が別の箇所にあった、実装中に読んだ別の箇所の誤りに気づいた、使ったツール・helper が誤った結果を返した
- 回避策で通した検証の、回避した失敗。回避策は、環境変数を外す、再実行で通す、テストを選んで外す など、正式入口をそのまま実行した結果ではない成功をいう

対象にしないもの:

| もの | 扱う場所 |
| --- | --- |
| この PR の変更で起きた失敗 | この PR で直す |
| レビューの指摘 | 判断の記録（`.agents/review-records.md`） |
| Issue の範囲を縮めた残り | 切り出し（`.agents/execution-budget.md`） |
| 確かめていない疑い | 記録しない |

## 扱い

- この PR では直さない。直すと PR の範囲が広がり、レビューと検証の対象が増える
- 起票しない。起票するか、既存 Issue に集約するか、見送るかは、事後調査が決める
- 回避策で通した結果で PR の作成まで続けてよいのは、原因がこの PR の変更でないことを確かめたとき（base でも同じ失敗が起きる、失敗した箇所をこの PR が変えていない など）だけである。確かめられなければ、今までどおり解消できない検証の失敗として止まる
- 最終化（マージ）の正式検証には、コマンド・環境・対象を変えた回避策（環境変数を外す、テストを選んで外す など）の結果を使わない。同じコマンドをそのまま再実行して通った場合は正式検証の成功として扱ってよいが、失敗した実行を記録する。回避策でしか通らなければ、最終化は今までどおり `stopped` で止まる
- 回避策を使ったら、回避した失敗を下の形で記録し、検証の結果を書く欄（PR 本文の検証、状況コメント、検証の記録）にも回避策を使ったことを書く。失敗の無い成功として書かない

## 記録する場所

| 場面 | 記録する場所 | 書く人 |
| --- | --- | --- |
| PR を作るまで | PR 本文の節 `## 作業中に判明した範囲外の不具合` | `issue-to-pr` |
| PR を作った後（レビュー修正のサイクル、CI の待機と再実行、ループの停止、最終化、マージの後） | PR への新しいコメント（下の「記録のコメント」） | 判明したセッション（`issue-to-pr`・`review-fix-planning` の planner・`pr-review-fix-loop` の司令塔） |

- PR 本文と、前に投稿したコメント（状況コメント・記録のコメント）は書き換えない。判明するたびに、記録のコメントを 1 件足す
- 状況コメントの形式（`.agents/review-records.md` 7 章）は変えない。状況コメントの本文では、回避策で通した検証を失敗の無い成功として書かない
- コメントを投稿できない（権限・ロック・API の失敗）ときは、利用者への報告に書き、投稿できなかったことも書く。PR に残らないので、事後調査の候補にならない

### 記録のコメント

1 行目は固定のマーカー、2 行目は見出しにする。事後調査は、書き込み権限のある投稿者（`OWNER`・`MEMBER`・`COLLABORATOR`）のコメントのうち、1 行目がこのマーカーのものだけを読む。本文に `<!-- review-fix-planning:` と `<!-- review-records:` で始まる文字列を書かない（判断の記録として読まれる）。

```markdown
<!-- out-of-scope-defects:v1 -->
## 作業中に判明した範囲外の不具合（<モデル識別子>）

判明した場面: <例: サイクル 2 の最終化の正式検証、CI の待機（run の再実行）、ループの停止（review の段階）> / その時点の PR の HEAD: `<SHA の先頭 12 桁>`

<下の「項目の形」の項目を 1 件以上>
```

## 項目の形

PR 本文の節では、何も無ければ「なし」と書く（確かめて無かったことと、書き忘れを区別する）。記録のコメントは、判明したときだけ投稿する。項目は 1 件ずつ次の形で書く。

```markdown
- <現象を 1 行で>
  - 確かめた commit と位置: `<SHA の先頭 12 桁>` の `<リポジトリからの相対パス>:<行>`
  - 確かめ方: <コードを読んだ／実行した（コマンドの形と結果）>。原因がこの PR でないことの確かめ方（base での再現など）
  - 回避策: <使っていない／何を外して・何をして検証を通したか>
```

PR とコメントは公開されるので、環境変数の値・トークン・ローカルの絶対パス・ログの全文を書かない。必要な行だけを選び、パスはリポジトリからの相対パスにする。
